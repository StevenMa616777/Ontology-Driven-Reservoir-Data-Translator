# 逻辑子表拆分需求、设计与现成模型验证方案

**日期：** 2026-09-23  
**状态：** 需求与验证方案已确定；进入现成模型调研和原型验证，尚未选定生产拆分模型  
**范围：** 对 OCR layout 已定位的父表进行逻辑子表发现、子表独立重识别、拆分复核和模型适用性评价

本文是 [`OCR_ENGINE_REQUIREMENTS_AND_IMPLEMENTATION_PLAN.md`](OCR_ENGINE_REQUIREMENTS_AND_IMPLEMENTATION_PLAN.md)
中“阶段 3：专用拆表模型与递归结构”的细化设计。上位文档负责整个 OCR Engine、表格树、人工复核和
`RawBlock` 链路；本文专门冻结“什么是逻辑拆表”、候选模型必须完成什么任务，以及下一阶段如何验证
现成模型。

本文不宣称 CTUNet、PaddleOCR 或其他候选已经满足项目目标。代码仓库中现有的
`PaddleSubtableProposalEngine` 仍是使用版面检测权重提出 table box 的安全原型，不是已经验证的逻辑拆表模型。

## 1. 背景与问题定义

当前 OCR pipeline 已能较好地完成：

- 页面 layout 和父级 table 区域定位；
- 文字检测与识别；
- 单张表格的结构和内容提取；
- OCR 结果到表格 `RawBlock`、人工复核及语义映射的衔接。

当前主要缺口是：layout 可能把一个视觉上连续的大区域识别成一张父表，但该区域实际包含两张或多张可以
独立解释的逻辑子表。直接把父表作为一张表识别，容易造成表头、列、单元格和文字归属互相污染；直接把父表
结果按数组行列切开，又会继承父表阶段已经产生的结构错误。

本项目所说的“表格拆分”必须同时完成两件事：

1. 识别父表中是否存在多个逻辑子表，并确定各子表的空间或单元格归属边界；
2. 从原始页面图像重新裁剪每个子表，分别完成结构和内容识别，生成可以独立进入下游的叶子表。

它不是修改父表的 `rows`，不是按 token 预算分块，也不是单纯检测单元格。

## 2. 已确定的设计决策

以下决定在现成模型调研期间保持不变，除非样本证据证明需要修改。

### D1. 拆分和识别是两个独立质量边界

“边界是否正确”与“边界内的表格内容是否识别正确”必须分开评价和记录。不得用整表平均 OCR 分数代替
拆分置信度，也不得用高拆分置信度证明子表文字和结构正确。

### D2. 拆分器应复用父表阶段的结构证据

拆分器可以同时使用：

- 父表原始裁剪图像；
- 单元格 bbox、多边形及行列关系；
- OCR token、文字内容及其 bbox；
- 有线表/无线表分类；
- 表头、合并单元格、rowspan/colspan 和结构 HTML；
- 父表及相邻标题、单位、脚注的 layout 证据；
- 各阶段置信度、质量标记和原始模型输出引用。

现有证据用于帮助判断如何拆分，但不能替代子表重新识别。

### D3. 每个子表必须从原始页面重新裁剪并识别

接受候选边界后，系统必须从带可逆坐标关系的原始页面图像裁剪子表，再分别运行表格识别。禁止仅从父表
已展开的 `columns/rows` 切片生成叶子表。父表识别、候选拆分和子表重识别结果分别保存，不互相覆盖。

### D4. 第一阶段不要求区分 `single` 与 `abstain`

为了先打通并验证整个流程，第一阶段允许“没有有效子表候选”同时表示：

- 模型认为父表无需拆分；
- 模型无法判断；
- 模型发生漏检。

上述情况统一保留父表作为候选叶子，并进入人工复核。只要尚未校准自动放行规则，就不要求生产契约增加
`single/split/abstain` 状态机。模型原生输出和分数仍须保存，便于未来区分。

### D5. 第一阶段以人工确认作为安全边界

候选拆分、未拆分父表和上下文归属均须人工确认。未解决的拆分问题不得进入语义映射。自动放行属于未来
高精度阶段，不是现成模型原型的前置条件。

### D6. 手动编辑边界是后续能力

第一阶段继续使用接受、排除、上下文归属和停止流程。后续人工复核可增加拖动、增加、删除、合并和拆分
子表边界，并在修改后从原图重新裁剪和识别。人工修改不得覆盖模型原始建议。

## 3. 术语与任务边界

| 术语 | 本文定义 |
| --- | --- |
| 父表 | 页面 layout 检出的候选 table 区域；它可能是一张表，也可能包含多张逻辑子表。 |
| 逻辑子表 | 具有一套可独立解释的表头—数据关系和适用上下文、可独立交给后续映射的表格。 |
| 子表候选 | 拆分器提出的 bbox、单元格集合或关系图分组，尚未成为已确认叶子。 |
| 叶子表 | 边界和必要上下文经复核，可以独立进入表格 chunking 的逻辑子表。 |
| 表格结构识别（TSR） | 识别一张表内部的行、列、单元格、合并关系或 HTML 结构。 |
| 表格内容识别（TCR） | 识别单元格中的文字和数值。 |
| 逻辑拆表 | 从一个父表中发现多张逻辑子表，并为每张子表建立可重识别的边界或单元格归属。 |
| 容量分块 | 在一张叶子表内部按完整行和 token 预算生成一个或多个 `RawBlock`；不改变逻辑归属。 |

以下能力不等同于逻辑拆表：

- 页面中普通 table detection；
- 父表内部的 cell detection；
- 对一张表恢复 HTML；
- 把一张大表按固定行数切成多个 chunk；
- 根据油藏本体概念或物理量语义分组。

拆分可以利用文字结构信号，但本阶段不要求拆分模型完成油藏本体映射。

## 4. 当前实现基线与缺口

### 4.1 已有可复用能力

- [`RecursiveTableEngine`](../src/reservoir_data_translator/ingestion/ocr/table_pipeline.py) 已提供递归、节点数、
  模型调用数、累计像素和调用间时间预算。
- [`SubtableSplitter`](../src/reservoir_data_translator/ingestion/ocr/table_pipeline.py) 已提供可替换的候选入口。
- [`TableTree`、`TableTreeNode`、`TableLeaf`](../src/reservoir_data_translator/ingestion/ocr/models.py) 已承载树、
  叶子引用、复核状态和来源坐标。
- [`OcrEngine._analyze_table()`](../src/reservoir_data_translator/ingestion/ocr/page_engine.py) 已把子表局部坐标
  回填到页面像素坐标，并将叶子表输出到 `OcrPageResult.regions`。
- [`PdfParser.finalize_ocr_review()`](../src/reservoir_data_translator/ingestion/pdf_parser.py) 已阻止未复核的拆分结果
  进入 chunking，并保存上下文归属。
- [`PdfParser._structure_and_chunk()`](../src/reservoir_data_translator/ingestion/pdf_parser.py) 已保证每个叶子表
  独立按行和预算切块。

### 4.2 现有拆分原型的限制

当前 `PaddleSubtableProposalEngine` 在父表裁剪上再次运行 `PP-DocLayout_plus-L`，只收集其中的 `table` 框。
该权重面向版面 table detection，没有使用本项目的逻辑子表标注进行训练或校准。因此：

- 它可能只返回覆盖整个父表的一个框；
- 它不能稳定理解共享标题、重复表头、列模式切换或复合关系表；
- 它的置信度是 table box detection 分数，不是逻辑拆分置信度；
- 它没有利用父表已经识别出的单元格、文字和结构证据。

### 4.3 进入真实模型验证前需要补强的契约

当前 `SubtableProposal` 只有 `bbox_pixels`、`confidence` 和 `reason`；`TableTreeNode.confidence` 当前主要承载
表格识别置信度。真实模型接入时至少要能分别保存：

- 子表边界置信度；
- 父节点本次整体拆分置信度；
- 父表和叶子表的结构/内容识别置信度；
- 候选所依据的单元格、token、结构或模型输出引用；
- 边界覆盖、单元格切断、遗漏和冲突等确定性检查结果。

原型调研可以先通过外部规范化 JSON 保存这些字段，不要求在选定模型前立即修改生产 dataclass。

## 5. 目标数据流

```text
页面原图
  → LayoutEngine 定位父表
  → ParentTableEvidenceExtractor
       ├─ 父表结构/内容识别
       ├─ cell boxes、行列/合并关系
       ├─ OCR tokens 与坐标
       └─ 标题、单位、脚注等相邻 layout 证据
  → LogicalSubtableSplitter
       ├─ 图像特征
       ├─ 单元格与结构图
       ├─ 文字与位置特征
       └─ 输出子表 bbox、cell membership 或关系分组
  → 确定性边界/覆盖/冲突检查
  → 从原始页面分别裁剪候选子表
  → 每个子表独立运行 TableRecognizer
  → TableTree + 候选 TableLeaf
  → 人工拆分和上下文复核
  → 已确认叶子表分别进入 PdfParser._structure_and_chunk()
  → table RawBlock → 语义映射
```

父表证据用于提出拆分；叶子表内容来自独立重识别。父表、中间节点和叶子表不能重复产生待映射块。

## 6. 功能需求

### R1. 模型无关的拆分输入

模型适配层应接收一个项目拥有的 `TableSplitInput`，而不是让生产管线依赖候选模型的原生类。建议概念字段如下：

```text
TableSplitInput
  run_id / page_number / parent_region_id
  parent_bbox_pixels / image_width / image_height
  parent_image_ref 或受控的图像对象
  parent_table_recognition
  detected_cells[]
  recognized_tokens[]
  structural_relations[]
  nearby_context_regions[]
  geometry_transform
  evidence_refs[]
  engine/model/config versions
```

候选模型可以只消费其中一部分，但适配器必须记录实际使用了哪些输入。

### R2. 模型无关的拆分输出

第一阶段的最小规范化输出为零个或多个候选，不强制 `single/abstain` 分类：

```text
TableSplitOutput
  proposals[]
    proposal_id
    bbox_pixels 或 cell_ids[]
    boundary_confidence
    reason
    evidence_refs[]
    raw_output_ref
  split_confidence
  structural_checks
  model/config versions
  duration/resource diagnostics
```

如果模型输出的是 cell relation graph，适配器可以形成单元格集合，再计算最小包围框；不得在转换时静默丢失
共享表头、非矩形成员或重叠关系。当前生产递归器只支持矩形裁剪，这类不兼容必须被标记并进入人工复核。

### R3. 置信度语义分离

目标表格树至少区分：

| 字段 | 所属对象 | 含义 |
| --- | --- | --- |
| `recognition_confidence` | 父表或叶子节点 | 当前裁剪内表格结构/内容识别可信度。 |
| `boundary_confidence` | 子表候选或子节点 | 此子表边界或成员归属的可信度。 |
| `split_confidence` | 被拆分的父节点 | 父节点应拆成当前整组子节点的整体可信度。 |
| `structural_checks` | 拆分决定 | 覆盖、重叠、单元格切断、遗漏、行列一致性等确定性检查。 |

这些字段用于诊断和未来校准；第一阶段不得仅凭它们自动放行。

### R4. 子表重新识别

- 候选边界必须映射回原始页面像素坐标。
- 每个子表从原始页面或记录了可逆预处理的干净来源图像重新裁剪。
- 子表识别单独产生结构、内容、置信度和原始模型输出。
- 不允许把父表的 `rows` 或 HTML 切片包装成子表识别结果。
- 可以复用父表 OCR token 作为辅助输入，但必须记录复用和重新推理的来源。

### R5. 递归与资源边界

继续使用现有深度、节点、模型调用、累计像素和调用间时间预算。新增模型不得绕过这些预算。时间预算当前不能
中断已经在运行的单次模型调用；真实模型验证必须单独报告单次推理尾延迟和内存峰值。

子节点必须小于父节点并产生可检查的进展。重复框、接近整父表的框、严重重叠、明显遗漏或切断单元格的候选
不得直接递归为可信叶子。

### R6. 第一阶段人工复核

第一阶段继续采用以下安全语义：

- 多个有效候选：展示父表、候选树和各子表识别结果，由人工接受或排除；
- 无有效候选：保留父表作为候选叶子，由人工确认；
- 边界冲突或证据不可兼容：禁止直接接受，允许停止；
- 标题、单位、脚注和说明：人工指定给全部、部分或不确定的叶子表；
- 所有阻断性项目解决后才允许进入语义映射。

### R7. 后续人工边界修正

后续 UI 应支持：

- 在父表原图上拖动候选边界；
- 增加、删除、合并或再次拆分候选；
- 边界吸附到 cell box 或网格线；
- 修改后局部重新运行子表识别；
- 同时保存模型建议、用户编辑操作和编辑后识别结果；
- 将经授权的纠正结果导出为模型评价或训练样本。

该能力不是本轮现成模型验证的阻塞条件。

### R8. 证据和可复现性

每次实验至少保存：

- 输入父表图像或稳定引用及其 hash；
- 页面、父表和候选子表坐标；
- 父表 cell/token/structure 证据；
- 模型、权重、代码版本、配置和运行环境；
- 模型原始输出及项目规范化输出；
- 各子表重识别结果；
- 阶段耗时、模型调用次数、显存/内存峰值；
- 人工标注、人工决定和失败分类。

调研脚本成功运行不等于生产 pipeline 已验证。研究环境、假组件测试、真实 CPU/GPU 推理和完整 GPU 到 LLM
验收必须分别报告。

## 7. 候选能力与角色划分

### 7.1 PaddleOCR / PP-TableMagic

PaddleOCR General Table Recognition V2 组合表格分类、表格结构识别、单元格检测、文字检测和文字识别。
`TableCellsDetection` 定位单元格，SLANet/SLANeXt 等恢复一张表内部结构。这些能力：

- 可以为拆分器提供 cell、网格、表头和文字位置证据；
- 可以在拆分后分别识别每张叶子表；
- 不能单独证明父表中存在几张逻辑子表；
- 不能把 cell detection 或 HTML 恢复直接宣称为逻辑拆表。

第一项建议基线是基于 Paddle cell graph 的可解释规则拆分器，例如综合列网格突变、重复表头、跨列局部标题、
大范围空隙和跨界单元格等证据。它用于候选生成和检查，不自动视为真值。

参考：

- [PaddleOCR General Table Recognition V2](https://www.paddleocr.ai/main/en/version3.x/pipeline_usage/table_recognition_v2.html)
- [PaddleOCR Table Cell Detection](https://www.paddleocr.ai/main/en/version3.x/module_usage/table_cells_detection.html)

### 7.2 CTUNet / ComFinTab

CTUNet 是当前优先调研的直接相关候选。它面向 compound table understanding，组合 cell detection、OCR、
位置、视觉和文本特征，通过关系图预测单元格类型及相互关系，并输出 table items。ComFinTab 提供约 10,000 张
复合财务表和 cell/关系标注。

它与本项目的潜在契合点：

- 任务明确涉及一张复合表中的多个 table items；
- 证明 cell、OCR、位置和文字特征可以复用；
- 关系图比纯 bbox detector 更适合表达共享表头和逻辑关联。

需要验证的风险：

- 其输出不是当前 `SubtableProposal(bbox)` 的直接等价物；
- 非矩形分组、共享表头和关系表可能无法无损转换成矩形递归裁剪；
- 训练域以公司年报/财务表为主，与油藏工程表存在分布差异；
- 开源实现基于较旧的 PyTorch、MMDetection 和 MMCV 栈，应隔离研究环境；
- 代码许可证、数据许可证和预训练权重条款须分别核对；
- 必须验证预训练权重能否获得、复现并在本项目样本上运行，不能只以论文或代码存在判定可用。

参考：

- [CTUNet 论文](https://davar-lab.github.io/files/mm2022_table/mmfp0553.pdf)
- [ComFinTab 数据集](https://davar-lab.github.io/dataset/comfintab.html)
- [DAVAR-Lab-OCR 实现](https://github.com/hikopensource/DAVAR-Lab-OCR)

### 7.3 通用 table detection / structure recognition 模型

Table Transformer、ClusterTabNet、UniTabNet 等可以作为父表检测、行列/cell 结构或特征提取的对照，但其公开
训练任务通常是 table detection 或单表 TSR，不应在未验证前视为 compound-table decomposition 模型。

它们可以承担：

- 替代或补充 Paddle 的 cell/row/column 证据；
- 形成结构质量对照；
- 为规则或关系图拆分器提供输入；
- 对拆分后的叶子表进行结构识别。

参考：[Microsoft Table Transformer / PubTables-1M](https://github.com/microsoft/table-transformer)

### 7.4 自训练 detector 或关系图模型

只有在现成模型和结构规则不能满足目标后，才进入训练或微调：

- 若目标子表基本都是互不重叠的矩形区域，可微调 `logical_subtable` bbox detector；
- 若存在共享表头、交错结构或 cell membership 比矩形更重要，应优先微调关系图/聚类模型；
- 训练数据必须遵守本项目的逻辑子表标注规则，不能直接把普通 table detection 标签当作真值。

### 7.5 视觉语言模型

视觉语言模型可以用于疑难样本解释、候选数量建议或标注辅助，但第一阶段不作为生产边界的唯一来源。其坐标
稳定性、可复现性、版本漂移、成本和延迟必须单独评价。

## 8. 现成模型验证问题

调研需要回答以下问题，而不是只回答“模型能否运行”。

### Q1. 逻辑拆分能力

- 能否识别父表中逻辑子表的数量？
- 能否处理左右并排、上下排列、共享标题和重复表头？
- 能否避免把多层表头、注释行或同一表的分段误拆成新子表？
- 输出是矩形 bbox、cell membership、关系图还是结构标记？
- 输出能否无损转换成当前递归裁剪和表格树契约？

### Q2. 子表内容质量

- 拆分后独立识别是否比父表一次识别更准确？
- 是否改善列对齐、表头归属、rowspan/colspan、单位和脚注处理？
- 是否保留小数点、正负号、指数、单位和关键工程数值？
- 是否存在拆分正确但子表 OCR/TSR 退化的情况？

### Q3. 安全与可复核性

- 是否提供边界、cell 关系、分数或其他可核查证据？
- 是否能保留原始输出并映射回页面坐标？
- 候选冲突、遗漏或不支持形状能否显式标记？
- 人工是否能看懂模型为何这样拆？

### Q4. 工程可用性

- 模型、权重、代码和数据许可证是否满足项目用途？
- 能否在当前 Windows/GPU 环境运行，还是需要隔离 Linux 环境？
- 初始化、推理、显存/内存和吞吐能否被生产资源边界接受？
- 是否支持稳定批处理、失败恢复和版本固定？
- 接入成本是适配、规则增强、微调还是重训练？

## 9. 样本与标注设计

### 9.1 最小样本类型

调研集至少覆盖：

1. 普通单表，验证误拆；
2. 左右并排子表；
3. 上下排列子表；
4. 共享总标题但各自拥有表头的子表；
5. 各子表共享单位或脚注；
6. 多层表头和合并单元格；
7. 无线表或弱边界表；
8. 列网格在中途变化的组合表；
9. 交错或非矩形逻辑关系；
10. 跨页续表；
11. 低清晰度、倾斜或局部缺损；
12. 关键小数、正负号、指数和单位容易误识别的工程表。

### 9.2 每个样本的人工真值

- 父表 bbox；
- 逻辑子表数量；
- 每张子表 bbox 和/或 cell membership；
- 子表列、行、合并单元格和表头关系；
- 标题、单位、脚注的归属；
- 关键单元格文字和数值；
- 是否允许只给出“不确定/需人工处理”；
- 对跨页、共享标题、非矩形关系的解释说明。

在标注规则稳定前不固定自动放行阈值。公开数据只能用于候选预训练或对照，不能替代项目样本真值。

## 10. 实验矩阵

建议对同一批冻结样本运行以下实验：

| 编号 | 拆分来源 | 子表识别 | 目的 |
| --- | --- | --- | --- |
| B0 | 不拆分，父表整体识别 | 当前 Paddle 表格识别 | 内容和结构基线。 |
| B1 | 当前 `PP-DocLayout_plus-L` 二次 table box | 当前 Paddle 表格识别 | 现有原型基线。 |
| B2 | Paddle cells/structure + 确定性结构规则 | 每个候选独立 Paddle 识别 | 验证现成结构证据能否支持可解释拆分。 |
| M1 | CTUNet 原始预训练输出 | CTUNet 原始 OCR/结构路径 | 验证论文方案和权重能否复现。 |
| M2 | CTUNet 关系分组适配为项目候选 | 每个候选独立 Paddle 识别 | 分离“拆分能力”和“内容识别能力”。 |
| M3 | 其他 TD/TSR 模型产生的 cell/structure 证据 | 每个候选独立 Paddle 识别 | 判断是否比 Paddle 证据更适合拆分。 |
| H1 | 模型候选 + 人工修正 | 每个修正候选独立 Paddle 识别 | 估计可达到的上限和人工成本。 |

不同实验必须使用相同页面渲染、父表坐标、样本版本和评价真值。不得把更高分辨率或人工裁剪带来的提升误归因
于拆分模型。

## 11. 评价指标

### 11.1 拆分指标

- 逻辑子表数量 exact match；
- 复合表成功拆分率和漏拆率；
- 普通单表误拆率；
- 候选 bbox IoU，或 cell membership precision/recall/F1；
- 关键单元格覆盖率；
- 单元格边界切断率；
- 父表内容遗漏率；
- 子表重复覆盖率；
- 共享标题/单位/脚注归属正确率；
- 不可转换或必须人工处理的比例。

### 11.2 子表结构和内容指标

- 行列数和合并单元格关系正确率；
- TEDS、GriTS 或候选模型原生结构指标；
- cell-to-text 归属准确率；
- 字符错误率/词错误率；
- 数值 exact match；
- 小数点、符号、指数和单位的关键 token 准确率；
- 与不拆分基线相比的逐样本提升、退化和无变化。

### 11.3 工作流和工程指标

- 每张父表需要人工接受、排除或修正的次数；
- 人工确认用时和无法确认比例；
- 初始化、证据提取、拆分、子表重识别各阶段耗时；
- GPU/CPU 内存峰值；
- 模型调用次数、累计处理像素和失败恢复情况；
- 叶子表到 `RawBlock` 的来源链完整性；
- 未确认拆分是否被可靠阻止进入语义映射。

调研初期不虚构生产阈值。先保存逐样本原始结果和错误分类，再根据样本规模与业务风险制定门槛。

## 12. 模型验证执行顺序

### 阶段 A：资料和可运行性审查

对每个候选记录任务定义、输入输出、代码、权重、许可证、框架版本、硬件要求和最后维护状态。首先确认是否真的
提供可用权重和推理路径；只提供论文或训练代码不计为“可直接使用”。

**交付：** 候选模型清单和适用性初筛表。

### 阶段 B：隔离原型

在不改生产 OCR pipeline 的情况下运行候选模型，保存原生输出，并通过研究适配器导出统一 JSON。旧依赖模型
优先使用独立环境或进程，避免污染当前 PaddleOCR 运行环境。

**交付：** 可重放命令、锁定环境、原始输出和规范化输出。

### 阶段 C：冻结小型标注集对比

使用同一批单表和复合表样本运行 B0、B1、B2、M1、M2。逐项检查拆分、结构、内容和资源开销，不以一两张
成功截图作为结论。

**交付：** 指标表、样本级差异和失败分类。

### 阶段 D：做出模型路线决策

将候选归入以下结论之一：

1. 可直接通过适配器接入；
2. 与 Paddle 结构规则组合后可用；
3. 需要在项目样本上微调；
4. 输出契约或效果不适合；
5. 许可证、依赖或资源成本不可接受。

只有完成此决策，才进入生产 `SubtableSplitter` 实现或训练工作。

## 14. 接入生产前的验收条件

候选模型只有同时满足以下条件，才可以作为正式 `SubtableSplitter` 进入生产路径：

1. 在冻结项目样本上完成单表和复合表评价；
2. 能输出或可靠推导可回填到原始页面的候选边界/成员关系；
3. 原始输出、模型版本、分数和证据可保存；
4. 子表可以从原图重新裁剪并独立识别；
5. 冲突、遗漏和不兼容形状不会静默进入映射；
6. 与现有表格树、复核和 `RawBlock` 来源链兼容；
7. 依赖、许可证和资源开销可接受；
8. 有明确的已知失败范围和安全停止路径。

本阶段不要求自动放行。人工确认后的正确端到端结果，是现成模型验证成功的最低工作流目标。

## 16. 当前开放问题

以下问题由样本和模型原型回答，不在本文中预设结论：

1. 项目主要复合表是否都能用互不重叠的矩形子表表达；
2. 共享表头和非矩形 cell membership 应复制为上下文、表示为关系，还是只允许人工处理；
3. CTUNet 预训练权重和依赖能否稳定复现，领域迁移程度如何；
4. Paddle cell graph 规则能否覆盖大部分工程表，是否需要学习模型；
5. 跨页续表属于拆分器、文档结构整理还是后续表格合并的职责；
6. 在多少标注样本和哪些失败类型覆盖后，才值得开始微调；
7. 未来自动放行需要怎样区分 `single`、`split`、`abstain` 和 `conflict`。

在这些问题得到证据前，所有拆分继续经过人工复核，不把候选模型输出描述为已确认事实。
