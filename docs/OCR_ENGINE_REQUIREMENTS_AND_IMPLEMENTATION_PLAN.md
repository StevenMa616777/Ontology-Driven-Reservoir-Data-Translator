# OCR Engine 需求文档与实现方案

**日期：** 2026-09-22  
**状态：** 分阶段实施中；接口、编排、复核与下游衔接已实现，逻辑拆表模型效果仍待样本验证  
**范围：** 扫描 PDF 的页面 OCR 编排、复合表格拆分、OCR 人工复核及与现有 `RawBlock` 链路的衔接

本文记录当前讨论已确定的需求和建议的实施顺序。它是 [`PDIE_dev_spec.md`](../PDIE_dev_spec.md) 中可替换文档处理能力的近期落地方案；不宣称该规格中的完整 Document IR、导出能力或独立微服务已经实现。本文也不改变原生文本 PDF、Ontology retrieval 或语义映射的既有职责。

## 实施进度（2026-09-22）

- 正式扫描 PDF 路径默认使用项目 `OcrEngine`，按版面区域分别调用可注册的文字检测、文字识别和表格处理组件；原 PP-StructureV3 composite 可通过 `RESERVOIR_OCR_BACKEND=paddleocr` 选择，供对照和回退。
- OCR 结果增加可选表格树、叶子引用、契约版本和阶段耗时。父表及节点识别结果保存在 OCR 原始证据中；叶子表经复核后按现有 `RawBlock` 格式单独 chunk。
- 递归表格处理设置深度、节点、调用、像素和调用间时间预算；当前时间预算不能中断已在运行的模型调用。现有候选边界组件使用独立调用的版面检测权重；它**没有经过逻辑子表任务标注和校准**，所有表格边界（包括模型认为无需拆分的父表）都必须人工复核，不能视为已满足 R3 的模型精度目标。
- 异步 OCR 审查已扩展拆分确认、排除和上下文归属；边界冲突不可直接确认。审查记录包含候选树与决定。
- 已用确定性假组件验证区域路由、原始页面坐标、复核闸门和叶子表独立 chunk；本机 CPU 已分别运行 Paddle 版面、文字和表格组件。尚未完成具有人工标注的逻辑子表数据集、准确率评价、完整 GPU 到 LLM 验收或生产负载性能测试。

## 1. 目标与边界

### 1.1 目标

1. 正式 PDF OCR 路径调用项目自己的 `OCREngine`。它以稳定的项目契约编排版面、文字和表格能力，当前可由 Paddle 模型或其子流程提供底层推理。
2. 各能力通过注册和适配器替换。模型原生对象、类别、坐标、置信度和表格格式不直接泄漏给 `PdfParser`、`RawBlock` 或语义映射层。
3. `TableEngine` 接收候选父表区域，使用**专用的逻辑子表拆分模型**提出并递归识别最小逻辑子表。该模型的选型和实际效果仍需验证，不能把现有父级版面检测的表现等同于子表拆分能力。
4. 保存父表及全部拆分过程形成的表格树；只有经过必要复核、可作为独立表解释的叶子表进入现有表格 chunking。树供来源追踪、监视、查看与复核，不作为整棵待映射表重复送入下游。
5. 低可信拆分与不确定上下文归属在语义映射前进入人工复核，保留原始证据和用户决定，减少 LLM 对视觉结构及来源边界的猜测。
6. 当前以进程内 Python 类和明确的接口实现上述概念；为未来迁移为文档处理微服务保留可序列化、可版本化的请求、结果和错误契约。独立部署不是本阶段交付条件。

### 1.2 本阶段不承担的工作

- 不把 OCR 拆到文字方向分类、表格单元格检测、阅读顺序等每个底层模型各有一个可替换接口。它们可由所属 Engine 内部组合。
- 不要求递归拆表模型判断油藏本体概念、流体相别或物理量；这属于后续语义映射。拆分依据必须来自文档可核查的视觉、文本和表格结构证据。
- 不用按 token 的行分组代替逻辑拆表，也不为了表达表格树而大规模改写现有 `RawBlock` 结构。
- 不在本阶段引入 HTTP 微服务、队列、分布式存储或通用文档格式扩展。

## 2. 当前实现基线

| 环节 | 当前事实 | 本方案需要补齐的能力 |
| --- | --- | --- |
| 正式 PDF OCR | [`PdfParser._ocr_page()`](../src/reservoir_data_translator/ingestion/pdf_parser.py) 渲染页面后调用 `OcrBackend.analyze_page()`；[`PaddleOcrBackend`](../src/reservoir_data_translator/ingestion/ocr/paddle_backend.py) 一次调用 PP-StructureV3 并适配结果。 | 由项目 `OCREngine` 编排实际组件并实现同一页面出口。 |
| 可替换接口 | [`components.py`](../src/reservoir_data_translator/ingestion/ocr/components.py) 已定义 Layout、TextDetection、TextRecognition、Table、Composite 的协议、注册表和实验用顺序编排。 | 按 layout 区域裁剪与路由、组件适配、页面结果汇总和正式路径接入。 |
| OCR Lab | [`build_default_engine_registry()`](../src/reservoir_data_translator/ocr_lab/service.py) 目前只注册整套 Paddle composite 基线；逐项组件接口主要由假实现验证。 | 注册真实组件，并能查看阶段结果、坐标和表格树；保留 composite 对照。 |
| 表格数据 | `PaddleOcrBackend` 将 HTML 表格展开成单个 `OcrTable(columns, rows, metadata)`；`OcrRegion` 只能直接携带这一张表。 | 在变成叶子表前，表达父表、候选子表、证据和拆分决定。 |
| chunking | [`PdfParser._structure_and_chunk()`](../src/reservoir_data_translator/ingestion/pdf_parser.py) 关联表题和章节；`_split_table_rows()` 在一张表内按完整行与 token 预算切分。 | 先输入各个逻辑叶子表，再分别执行现有容量切分。 |
| OCR 复核 | `OcrReviewSession` 与后台任务已在映射前暂停；当前决定仅为区域 `include/exclude`，然后整体 `continue/stop`。 | 增加拆分确认及上下文归属复核；保持现有逐项决定与整体停止/继续两级控制。 |

当前以 `RawBlock` 为语义映射的处理范围。表格块的内容是 `columns + rows + metadata`，而不是原始 HTML 或普通文字。语义映射逐块调用，故逻辑子表边界应在 `RawBlock` 生成之前确定。

## 3. 术语及处理层次

| 术语 | 含义 |
| --- | --- |
| 父表 | 页面 layout 检出的候选 table 区域及其原始图像、原始模型输出；可能是一张表，也可能包含多张逻辑子表。 |
| 逻辑子表 | 共享一套可解释的列关系与适用上下文、可独立交给后续映射的一张表。最小是**逻辑边界**，不是最少行数。 |
| 表格树 | 父表、各级候选子表、叶子表以及拆分证据和决定的层级记录。即使未拆分，也应保留父节点与最终叶子身份。 |
| 叶子表 | 已通过结构检查和必要复核、允许进入现有 chunker 的逻辑子表。 |
| 容量分块 | 在一张叶子表内部按完整行及 token 预算形成一个或多个 table `RawBlock`；不改变子表归属。 |

设计中的数据流：

```text
PDF 页面 → 渲染图像 → 项目 OCREngine
                       ├─ LayoutEngine：父级区域、类别与位置
                       ├─ TextDetectionEngine + TextRecognitionEngine：文字行与内容
                       └─ TableEngine：父表识别 → 专用拆表模型 → 递归子表识别
                                           ├─ 表格树及原始证据 → 持久化、查看、复核
                                           └─ 已确认叶子表 → OcrPageResult.regions
            → PdfParser 共享结构整理 → 每个叶子表单独按行 chunking
            → RawBlock → 候选检索与语义映射
```

页面可能包含多个互不相关的 table 区域；每个父表独立建立树。一个叶子表可以产生多个容量块；父表或中间节点不能再产生一份重复的映射块。

## 4. 功能需求

### R1. 项目 OCR 编排入口

- `OCREngine` 满足现有 `OcrBackend.analyze_page(image, page_number, languages) -> OcrPageResult` 的正式页面调用需求，或通过兼容适配器提供完全等价的出口。
- 引擎选择与运行参数由显式配置或注册表确定；记录实际运行的 Engine、模型、配置版本。不得以某个 Engine 已注册推断模型已成功初始化或已在真实页面运行。
- 版面先提供候选区域。文字能力识别文字区域；表格能力处理表格区域。允许同一模型在内部复用推理结果，但项目输出必须能确定每个结果所属的来源区域。
- 保留现有 PP-StructureV3 整套 composite 实现，作为迁移期间的可运行基线与对照；它不被描述为已经可逐个替换的组件链路。

### R2. 组件间适配契约

- 接口定义图像/裁剪的颜色格式、尺寸、坐标系、像素框或多边形、区域 ID、父区域 ID、阅读顺序、语言、置信度及缺失值语义。
- 所有子区域与文字/表格框都能回填到**原始页面像素坐标**，供 `PdfParser` 转换成 PDF 页面坐标。若预处理改变几何形状，记录正逆变换；无法回填时不得把处理后坐标冒充原始坐标。
- 适配器处理底层模型的类别映射、局部裁剪坐标、置信度、表格 HTML/单元格结构及文字归属。若关联证据冲突，显式产生质量标记或错误，不按模型结果列表的偶然顺序配对。
- 输出可序列化且带契约版本，使进程内调用与未来远程调用使用同一含义；本阶段不承诺网络协议细节。

### R3. 专用模型驱动的逻辑拆表

- `TableEngine` 为表格处理入口。它可以组合表格识别能力与专用的**子表边界/结构拆分模型**；后者提出“是否拆分、如何拆分”，不做本体映射。
- 拆分应同时利用原始父表图像及可用的表头、网格、单元格、文字和空间信息。子表再次识别时，应从原始页面图像裁剪，不能只从已展开的 `columns/rows` 反推图像区域。
- 递归必须有可检查的进展：子节点范围小于父节点；不得无限重复同一候选；限制深度、节点数、模型调用数与像素/时间预算。候选重叠、遗漏和互相冲突均需记录。
- 任何被接受的叶子表必须具有一致的列数和行宽，并保留可能的多层表头、合并单元格及单位信息。不能只凭第一行就是表头的假设强行宣告结构正确。
- 若模型认为父表本身已经是一张逻辑表，则父节点也是最终叶子；无需为了“递归”强行拆分。
- 原始父表识别、候选拆分、重识别结果及最终决定均保留；不得用纠正后的结果覆写原始证据。

### R4. 表格树与下游叶子表

- OCR 分析结果需提供表格树及叶子表的稳定标识和相互引用。建议在 OCR 层扩展可选、版本化的表格分析记录；正式 `OcrPageResult.regions` 仍提供可供现有 `PdfParser` 消费的叶子表区域。具体采用 `OcrPageResult` 可选字段还是同一结果包装对象，在阶段 1 以兼容性验证后固定。
- 每个树节点至少可追溯页面、父节点、原始像素范围、模型输出/证据引用、拆分原因、置信信息、状态及用户决定。容量分块应引用其叶子表 ID，并记录叶子表内的行范围。
- 树的展示与保存是 OCR 证据的一部分；语义映射的当前 `raw_block` 只包含该叶子表的处理块及经确认适用的上下文，不附带整棵表格树或其他子表的内容。
- `RawBlock` 的 table 基本形状维持 `columns + rows`。确有需要时只增加兼容的来源引用或元数据，不引入新的嵌套 table 内容类型。

### R5. OCR 阶段复核与映射闸门

- 专用模型置信不足、无可信置信信息、边界重叠/遗漏、标题与列结构冲突或结果不一致时，产生针对**逻辑拆分**的复核项；不能仅凭整表平均 OCR 分数决定可信。
- 拆分后的标题、单位、脚注、说明等上下文归属由人工复核确认。界面可显示模型建议，但不得把相邻位置直接当作已确认归属；允许“全部子表／指定子表／无法确定”，并记录所依据的原始区域。
- 复核展示父表原图、原始模型结果、候选树、各子表裁剪和识别数据、问题原因。用户可确认或调整拆分与归属；若本阶段 UI 不支持直接绘制边界，需有安全的“无法确认/停止”路径，不得将未确认猜测送入映射。
- 保持“逐项处理后整体停止或继续”的既有工作流。只有所有阻断性 OCR/表格复核项已解决，才允许进入语义映射。现有 `include/exclude` 区域决定不能被假定为已确认子表边界或上下文。
- 未能可靠拆分或确认的内容继续保存在原始证据和审查记录中；不得悄悄丢弃，也不得以不确定叶子表生成貌似完整的自动映射结果。

### R6. 诊断、兼容和资源保护

- 记录逐页及逐阶段耗时、选中 Engine/模型版本、失败阶段、拆分节点数、复核项和叶子表至 `RawBlock` 的来源链。原始 OCR JSON 和中间结果继续可读、可下载；即使后续阶段失败，也保留已发生调用的证据。
- 原生 PDF 解析与共享 `_structure_and_chunk()` 的现有行为在未涉及表格递归的文档上保持可用；混合 PDF 支持不在本方案中顺带扩展。
- 延续现有页面与 OCR Lab 像素保护，并在递归处理里设置节点、调用及时间预算。性能评价使用实际页数、表格数量和图像分辨率，不以文件字节大小或单次成功运行代表可用性。

## 5. 推荐实现方案

### 阶段 0：基线与评价样本

收集有代表性的扫描页：普通文字、单张表、并排子表、上下排列子表、多层表头、交错排版、模糊边界、标题/单位位置含糊及关键数字容易误识别的样本。人工标注父表、逻辑子表、字段/行、上下文归属、允许的“不确定”结果。保存当前 composite 输出、原始 JSON、运行环境及阶段耗时，作为迁移对照。

**交付：** 可重放的样本清单、标注规则、基线结果和失败分类。样本标注先于确定拆分置信门槛。

### 阶段 1：冻结 OCR 层接口与来源契约

明确 `OCREngine`、注册表和适配器的职责；固定页面/裁剪输入、结果、坐标变换、错误及版本字段。设计表格树与叶子表引用方式，并验证旧 `OcrPageResult`、OCR Lab、`PdfParser` 是否能兼容新增的可选分析数据。以确定性的假 Engine 验证路由与组装，不在此阶段引入真实拆表模型。

**交付：** 版本化契约、兼容方案、契约测试和错误目录。

### 阶段 2：打通真实的项目 `OCREngine`

实现页面路由与归一化汇总；接入真实 Paddle 版面、文字检测/识别和表格子流程的适配器。注册选择当前可用的实现，延迟加载并复用模型。正式 PDF 路径可显式选择项目 `OCREngine`，OCR Lab 可独立检查组件结果；保留整套 PP-StructureV3 基线用于逐页对比。

**交付：** `PdfParser` 可消费新引擎的有效 `OcrPageResult`；普通文字与单表样本具备坐标、内容及来源的可核查对照。这里须实测 Paddle 的独立接口、模型组合和性能，不能以协议测试替代真实推理验证。

### 阶段 3：专用拆表模型与递归结构

依据阶段 0 样本选择或训练专用拆表模型；它须能够对父表提出子表候选，并给出可核查的边界/结构信息。先单独评估模型，再接入 `TableEngine` 的递归、终止条件、结构检查、树保存和叶子输出。仍以现有 `RawBlock` 格式为下游出口。

现成模型调研、拆分输入输出、评价样本、实验矩阵和接入条件见 [`LOGICAL_TABLE_DECOMPOSITION_REQUIREMENTS_AND_MODEL_EVALUATION.md`](LOGICAL_TABLE_DECOMPOSITION_REQUIREMENTS_AND_MODEL_EVALUATION.md)。

**交付：** 对多表组合样本产出可追溯的树与正确的叶子表；普通单表不被无故拆分；不确定结果能弃权并触发复核。

### 阶段 4：人工复核及现有 chunking 衔接

扩展异步 OCR 复核会话，加入拆分和上下文归属决定；保存审查记录。复核完成后仅将已确认叶子表送入 `PdfParser` 的共享结构整理和按行容量分块。UI 能从处理块定位叶子表、父表和原始图像，并清楚显示未解决项。

**交付：** 一张子表可分成多个容量块，但两个逻辑子表的行不会合入同一 `RawBlock`；未解决复核项阻止语义映射。

### 阶段 5：端到端验收与未来服务边界

分别评价版面区域、文字、父表识别、子表拆分、表格数据、复核准确性、chunk 边界、候选检索与最终映射。检查多页/多表负载的延迟、内存峰值与失败恢复。根据稳定后的请求/结果契约，再制定独立进程或微服务部署方案；本阶段先记录迁移条件，不实际拆服务。

**交付：** 分阶段质量报告、回归样本、已知失败范围及微服务迁移所需的接口/资源约束。

## 7. 验收要点

1. **组件可替换：** 替换一个已注册的布局、文字或表格实现，`PdfParser` 和 `RawBlock` 不需理解该供应方的原生数据格式；真实模型路径与假 Engine 路径分别验证。
2. **正确分层：** 单张逻辑表进入一次叶子表处理；复合表先拆成叶子表，再各自按完整行/预算分块；父表不作为重复映射块出现。
3. **无证据不确认：** 缺少可靠拆分或上下文归属时保留原始结果与候选，生成复核项；未确认的叶子表和上下文不进入自动语义映射。
4. **来源可重建：** 从任一 table `RawBlock` 可找到叶子表 ID、父表 ID、行范围、原始页面坐标、相关原始 OCR 结果和人工决定。
5. **兼容与回归：** 原生 PDF、普通 OCR 文字、单表、OCR Lab 和既有低置信度区域复核均有针对性回归；真实 Paddle 推理结果、完整 GPU 到 LLM 流程与单元/假后端测试分别报告，不混称为同一种通过。
6. **性能与稳定性：** 记录初始化、页面渲染、各模型推理、递归、复核等待外的处理时间、内存峰值和调用次数；达到预算时明确失败或待复核，不无限递归或静默降级。

具体准确率、置信门槛和时延上限应根据阶段 0 的样本规模及真实运行环境设定，本文不虚构数值目标。

## 8. 仍需通过样本或原型确认的事项

这些是实施任务，不需要重新讨论已经确定的总体方向：

1. **拆表模型选型与训练数据：** 目前没有验证过能满足本项目最小逻辑子表定义的专用模型。需比较可独立调用的候选模型或训练方案，尤其考察无网格、多层表头、并排及交错结构。
2. **逻辑子表标注规则：** 对跨页连续表、共享标题/单位、合并单元格、多层表头和子区域重叠建立一致的人工标注准则；避免将注释或容量行组误标为独立子表。
3. **表格树的兼容载体：** 在 `OcrPageResult` 上增加可选字段，或使用带 `page_result` 的 OCR 分析包装对象；以 `PdfParser`、复核会话和未来序列化的最小兼容改动决定。
4. **复核交互深度：** 首版是否允许在 UI 内直接调整子表框，还是先支持确认/拒绝候选并转 OCR Lab 手动重试；两种情况下都必须保留停止及证据保存路径。
5. **置信度校准与放行规则：** 分别评价父表定位、拆分、表格内容及上下文归属；单一平均分不能替代结构冲突检查。门槛在标注样本上校准后固定并版本化。

上述事项由各阶段样本和原型给出答案。在它们得到验证前，不能声称专用拆表模型已经可靠，或把自动拆分结果直接当作事实进入正式映射。
